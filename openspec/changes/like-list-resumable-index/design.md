## 背景

现有点赞列表流程从游标零开始，在 `ListDownloadViewModel` 中保存映射后的行，并把每个服务端分页直接追加到 UI 列表。点赞接口接受不透明的 `max_cursor`，不提供页码、反向游标或排序参数。变更动机见 `proposal.md`，行为契约见 `specs/resumable-liked-list-index/spec.md`。

## 目标与非目标

**目标：**

- 在不把所有分页保存在 UI 中的前提下，让长点赞列表可恢复、可限定条数地遍历。
- 保留足够的稳定元数据，以确定的来源顺序或作品创建时间查询已索引条目。
- 通过可复用的列表来源身份隔离持久化数据，同时本次只启用点赞来源。
- 在游标陈旧时安全恢复，避免静默丢弃部分索引。

**非目标：**

- 从服务端反向请求点赞作品，或跳转到任意页。
- 承诺精确的点赞发生时间；当前接口提供的是作品 `create_time`，不是经确认的点赞时间。
- 改变作品、收藏、收藏夹或合集的获取行为。
- 将带签名的媒体 URL 作为持久化下载凭据。

## 决策

### 将索引会话与索引条目分开持久化

新增 Room 支持的会话记录：以通用来源身份（`sourceType`、所有者 sec-user ID、可空的未来收藏夹 ID）为键；另设以来源身份和 aweme ID 为键的条目记录。会话保存状态、配置上限、索引数量、下一游标、最后成功分页时间和可恢复错误状态；条目保存稳定作品元数据、来源序号和创建时间。

这种拆分将生命周期检查点与条目分离，使未来增加收藏夹来源成为增量改动。已否决单个序列化对象或 SharedPreferences 游标，因为它们无法提供持久化去重、有序查询和来源隔离。

### 将 `max_cursor` 视为不透明值，并仅在分页成功的事务后检查点化

新会话以游标零开始。每个成功分页都在同一事务内更新去重条目并保存响应中的下一游标/状态。不得根据条目数量或用户输入的页数推导游标。

即使列表头部新增点赞，这也可保留可恢复的边界；但它不承诺服务端冻结快照，删除、转私密或远端重排仍可能产生缺项或重叠，由条目级去重处理。

### 用条数限制工作量，并使用接口允许的最大分页大小

向用户暴露最大索引条数，而不是 `max_cursor` 文本输入。索引请求使用既有客户端允许的最大值 `count=50`，并在达到配置的唯一条目上限或远端列表结束时准确停止。

已否决页码输入，因为服务端游标不是偏移量；也已否决持久化完整响应页，因为它会增加存储量，并保存没有持久价值的过期媒体 URL。

### 将索引元数据与新鲜媒体地址解析分开

索引条目保存稳定 ID 和展示/排序元数据，不保存带签名的视频或图集 URL。持久化条目进入新的下载任务前，应用必须通过合适的当前 API 路径重新解析可下载媒体信息。

这样恢复索引后不会把过期签名 URL 当作有效地址。已否决复用缓存 URL，因为它们的有效期由远端服务控制，无法保证在进程死亡或稍后恢复后仍有效。

### 显式处理陈旧游标

错误、异常续拉数据，或与已保存 `hasMore` 状态矛盾的空分页，都会将会话置为 `RECOVERY_REQUIRED`；不得自动清空已有条目。用户可从头到尾建立新索引，并且只有确认后才替换会话。

已否决自动重启，因为它可能掩盖网络/认证错误并消耗大量流量；也已否决把异常空页标记为完成，因为这可能静默遗漏更早作品。

## 风险与取舍

- [服务端游标格式或保留策略变更] → 保持游标不透明、暴露恢复状态，并保留 ID 去重。
- [遍历期间新增点赞、作品删除或隐私变化] → 将索引描述为尽力而为的快照并保留远端顺序；可从头重新索引。
- [大型索引增加数据库体积] → 保存紧凑的规范化元数据而非原始 JSON/完整分页，并强制条数上限。
- [下载时重新解析媒体信息增加工作量] → 仅为选中的条目解析，并将其失败与索引完整性分开报告。
- [Room 迁移失败] → 增加经过测试的迁移，并保留幂等的重新索引逃生路径。

## 迁移计划

1. 新增数据库实体、DAO 查询和前向 Room 迁移，不改动既有下载记录。
2. 在既有点赞列表选择流程中发布索引入口；不自动让任何既有列表模式改用索引。
3. 索引失败时保留会话和条目，供恢复或显式重新索引。
4. 回滚时隐藏入口即可；新增表保持惰性，既有列表和下载流程不受影响。

## 开放问题

- 最大索引条数的 UI 形式（预设选项或经校验的数字输入）可在实施中决定，两者均满足有限索引需求。
- 首个版本可在索引 UI 中暴露来源顺序和作品创建时间排序；由于接口未提供经验证的点赞时间，专门的“最早点赞”文案延后决定。
