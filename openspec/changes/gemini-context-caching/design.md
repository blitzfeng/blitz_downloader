## Context

见 proposal.md「Why」——本次只做隐式缓存的启用条件(prompt 前缀顺序),不做显式缓存的资源生命周期管理。这里补充与用户核实后得到的关键事实与不确定性,供后续独立变更(显式缓存)参考。

`GeminiProvider.generateTagSuggestion` 当前的 `buildTagSuggestionPrompt` 顺序是:

1. 固定指令文本(两条编号说明)
2. `desc`(逐视频文案)
3. 标签词表 JSON(`gson.toJson(request.tagVocabulary)`)
4. 作者历史先验 / 个人偏好摘要 / few-shot 样例
5. 结尾 schema 提醒句

`desc` 夹在指令说明和标签词表之间,导致"跨请求不变的那部分内容"(1 + 3)不是一段连续前缀——即使 Gemini 服务端想做隐式缓存匹配,前缀在第 2 步就被逐视频变化的 `desc` 打断了,不可能命中。这是本次变更要修的唯一问题。

**与用户核实到的信息,以及为什么不采信任何一个具体数字**:

- 一份 Google Cloud Enterprise Agent Platform 官方文档(上次变更调研时抓取)写显式缓存最小 token 门槛是 4096(`gemini-3.x` flash 系列)。
- 用户与另一个 Gemini 会话核实后转述:该门槛在 Generative Language API(即本项目实际调用的 `generativelanguage.googleapis.com` 路由)已针对 `gemini-3.8-flash` 调整为 32768,理由是"服务器内存调度优化"。这个说法**没有给出一手可核查的来源**(既非 changelog 链接也非真机响应截图),且与项目已经踩过的坑同构——`CLAUDE.md` 里 `mediaResolution` 字段名/大小写就两次被"过期文档/二手示例"坑过,最终都是靠真实请求的 400 响应才纠正。
- 两份信息互相矛盾,且都可能因 Gemini 3 系列的密集迭代而在写下这行字的当下已经又变了。

**结论**:显式缓存要不要做、门槛具体是多少,都不在本次变更里下定论,留给后续独立变更在真正要实现显式缓存时用一次真实的 `POST /v1beta/cachedContents` 请求现场探测(故意发一份预估接近某个候选门槛的内容,看 200 还是 400,400 的错误信息通常会直接带上实际要求的最小值,不需要靠猜)。本次变更只做"零成本、零新增失败面"的隐式缓存启用条件,不依赖这个门槛数字。

## Goals / Non-Goals

**Goals:**
- 让 AI 建议标签请求里跨调用不变的内容(通用指令 + 标签词表)成为一段连续、顺序稳定的前缀,为 Gemini 服务端的隐式缓存创造命中条件。
- 改动前后,发给模型的信息内容保持一致(只调整顺序,不删减、不新增),`generateTagSuggestion` 的输入输出契约、失败处理、结果过滤逻辑不变。
- 不引入任何新的网络调用、状态存储或失败面。

**Non-Goals:**
- 不实现显式缓存(`cachedContents` 资源的创建/获取/更新/删除),不做缓存元数据持久化——这些全部推迟到后续独立变更,且门槛值必须届时现场验证。
- 不在本次变更里新增任何用于展示"是否命中隐式缓存"的 UI 或结构化日志字段;验证依赖现有 `LoggingInterceptor` 已经完整打印的响应体,人工核对即可,不值得为一个还不确定是否要长期维护的验证步骤新增代码。
- 不评估/决定是否最终需要显式缓存——那是根据本次隐式缓存真机验证结果之后才能做的判断,不在本次变更范围。

## Decisions

### 1. 只调整 `desc` 的位置,不引入新的 prompt 拼装抽象
把 `buildTagSuggestionPrompt` 里 `desc` 那一段(`if (request.desc.isNotBlank()) { appendLine("视频文案：...") }`)从"指令说明之后、标签词表之前"挪到"标签词表 JSON 输出之后、作者历史先验之前"。不拆分成两个独立函数(如"可缓存前缀"/"动态后缀"这类抽象)——那属于显式缓存才需要的边界划分(需要精确知道"前缀到哪里为止"以便单独发送去创建缓存资源),隐式缓存不需要客户端划分边界,只需要内容顺序本身稳定,继续用一个 `buildString` 顺序拼接即可,改动面最小。

**替代方案**:提前按显式缓存的思路拆出 `buildCachePrefix`/`buildDynamicSuffix`(上一版方案的做法)。放弃的原因是:在显式缓存的门槛与是否要做都还不确定的情况下,提前做这个拆分是在为一个可能不会发生的后续变更预先设计抽象,不符合"不为假设的未来需求预先设计"的项目约定;等真正要做显式缓存时,那次变更本身就需要重新审视这个拆分点(比如届时可能改用 `systemInstruction` 承载前缀而不是 `contents`),现在拆好的抽象大概率还是要改。

### 2. 验证方式是人工读日志,不新增结构化观测代码
`GeminiProvider.LoggingInterceptor` 已经把完整响应体(含 `usageMetadata`)按 3000 字符分块打印到 `Log.d(TAG, ...)`。`usageMetadata.cachedContentTokenCount` 一旦出现,直接在这份已有日志里可见,不需要在 `GeminiGenerateContentResponse`/`GeminiModels.kt` 里新增字段解析。真机验证步骤是:短时间内连续对多条视频点「AI 建议」,`adb logcat` 搜 `GeminiProvider` 标签,对比几次响应体里 `usageMetadata` 段落是否出现该字段、数值是否 > 0。

**替代方案**:在 `GeminiGenerateContentResponse` 里新增 `usageMetadata: GeminiUsageMetadata?` 字段并在代码里显式读取、打印一条专门的验证日志。放弃的原因同 Decision 1——这是为了验证一个阶段性假设而引入的代码,验证完之后如果决定做显式缓存,这个字段解析未必会以现在的形态被长期需要(届时更可能是为了监控命中率而做,应该放在那次变更里按那时的实际需求设计)。

## Risks / Trade-offs

- **[风险] 隐式缓存的命中条件(时间窗口、模型是否覆盖 `gemini-3.8-flash`)本身也未经证实** → 与显式缓存门槛同理,不采信任何未经证实的具体数字(比如"1 分钟窗口"),按 Goals 里定义的验证步骤真机观察,结果本身就是答案。就算隐式缓存这次也不生效(比如 3.8 暂不支持,或窗口太短覆盖不到真实使用节奏),本次改动的代价也只是 `desc` 顺序调整,不会比现状更差,且为将来做显式缓存先把前缀理顺了,不是浪费。
- **[风险] 调整 `desc` 的位置可能轻微影响模型输出的顺序敏感性(LLM 对 prompt 顺序不是完全不敏感)** → 无法用 spec 场景做形式化验证,只能靠人工核对几次真实建议结果与调整前是否明显跑偏(见 tasks.md 验证步骤);这是内容顺序变化本身不可避免的固有风险,不是本次实现引入的额外缺陷。
- **[权衡] 本次改动价值上限较低(隐式缓存折扣、命中窗口都不受客户端控制)** → 这正是选择先做这一步的原因:上限低但下限是零风险、零新增代码复杂度,用最小成本换取"是否需要再投入显式缓存"这个问题的真实答案,避免在门槛数字不明确的情况下过早投入。
