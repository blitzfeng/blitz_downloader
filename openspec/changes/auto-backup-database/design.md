# Design

## Context

动机见 [proposal.md](proposal.md)，验收行为见 [数据库备份规范](specs/database-backup/spec.md)。

当前 `DatabaseBackupManager.backupNow()` 在公共目录 `Download/bDouyin/backup/backup_yyyyMMdd_HHmmss/` 依次复制主库、WAL 和 SHM；`listBackups()` 仅凭主库文件存在列出副本。检查点之后仍可能有并行业务写入，顺序复制不能保证文件属于同一时点。当前对共享 writableDatabase 使用 `use` 也不适合自动调用，应移除关闭共享连接的行为。

`SettingsViewModel` 只在自身实例中限制 busy，不能排除自动操作的并发。`BlitzApp` 已有应用级 IO 协程和偏好任务恢复，后台服务启动不应被视为用户打开 App。数据库正在另一项需求中升级，实施时必须读取实际 Room 版本，不能覆盖其迁移或新增表。

## Goals / Non-Goals

**Goals:** 不阻塞首屏；输出可验证、独立恢复的完整数据库；明确失败后的备份和清理边界；适配 minSdk 24，不依赖联网。

**Non-Goals:** 不做定时唤醒、云备份、媒体备份、API Key 导出、自动恢复或设置页重构。本版固定默认启用，暂不增加周期和保留天数配置项。

## Decisions

### 1. 时间与触发

- 5 天定义为 432000000 毫秒，1 个月定义为固定 30 天（2592000000 毫秒）；均严格大于才触发。
- 用 `Application.ActivityLifecycleCallbacks` 聚合可见 Activity，结合延迟确认退出前台（约 700ms）和 `isChangingConfigurations`，识别首次打开及后台返回。所有 Activity 共用一个前台会话编号；不在 `Application.onCreate` 直接备份，不把每次 `onResume` 都当新会话。不增加 ProcessLifecycleOwner 依赖。
- `BlitzApp` 持有唯一 `DatabaseBackupCoordinator`，前台会话只发出一次检查请求；IO 工作在应用级 `SupervisorJob` 中执行，切换页面不取消。进程终止后，下次前台重新判断，不承诺后台任务必定完成。
- 存储权限弹窗返回后可重新请求检查，仍经过同一互斥和成功时间判断；失败冷却可在实际权限状态变化后解除一次。无权限不主动弹新的授权流程，继续使用现有权限入口。
- 每次真正检查都扫描已发布副本，不能仅看 SharedPreferences 的时间。手动有效副本也计算周期。目录不可读取必须区分“未知”与“没有副本”，不能按空列表执行删除。

### 2. 统一入口与并发控制

协调器提供前台检查、手动备份、File 恢复、SAF 恢复四类入口，使用同一个进程级 Mutex。设置页 busy 与原确认流程保留；所有旧入口转至协调器，不能绕过锁。等待锁后重新扫描，再决定是否自动备份或删除，避免等待期间新建副本导致重复。

执行顺序：扫描 → 判断时间和权限 → 如到期则创建并校验发布新副本 → 清理 → 记录结果 → 前台提示。新备份失败本轮不清理；未到期也进行清理。成功副本发布与清理是两个独立结果，不能把删除失败算作备份失败。

恢复也取得同一锁，恢复目标在锁内重新核验。恢复流程保持关闭旧库、替换文件、重启进程及 SAF 兼容行为；协调器不在等待重启期间启动新检查。

### 3. 一致快照：事务内逻辑复制到独立 SQLite 数据库

采用不依赖系统 SQLite 新版本或新 native 库的逻辑快照。相比直接复制正在写入的 DB/WAL，该方案能明确界定事务视图；相比仅用 `VACUUM INTO`，不受旧 Android SQLite 不支持该指令的限制。

1. 在内部 cache 专属临时目录创建目标 SQLite 数据库，源库通过现有 Room 单例访问，禁止关闭其连接。
2. 在一个 Room `withTransaction` 内读取源库 `sqlite_master`、`user_version`、`application_id` 和全部业务表数据，包含 `room_master_table` 和本版新增偏好表。逐行读取并绑定原始 SQLite 类型（NULL/整数/浮点/文本/BLOB），不把所有行积累在内存中。
3. 目标库暂时关闭外键检查，在自己的事务内先建普通表，复制数据，再恢复显式索引、视图和触发器，避免复制时触发业务触发器。SQL 为 NULL 的自动索引由表定义生成；`sqlite_sequence` 按源值恢复。引用的表名按 SQLite 标识符规则转义。当前无虚拟表的前提在实施时检查；发现不支持的结构直接失败，不能静默漏表。
4. 保存数据库版本和 Room identity；完成目标事务后关闭目标库，让输出为不依赖 WAL/SHM 的单文件。源 Room 事务结束后业务写入继续，外部存储复制及哈希计算在事务之外进行。
5. 在独立只读连接对副本执行 `PRAGMA quick_check`、`foreign_key_check`，核对表集合、行数、版本和 Room identity。失败则不发布。确认外部发布文件字节数及 SHA-256 与已验证临时快照一致。

该过程会短暂串行化源库写事务，不能阻塞主线程；快照只含元数据，不含视频。任务记录事务耗时、总耗时及字节数，并以并发写入和较大元数据集验证等待时间。保留原手动入口但升级为同一快照实现，不维持不一致的旧复制算法。

### 4. 发布与兼容布局

新副本布局沿用 `backup_yyyyMMdd_HHmmss` 前缀，增加毫秒与随机后缀防止碰撞，例如 `backup_20261127_093000_123_a1b2/`，含 `blitz_downloader.db` 和 `manifest.json`。

manifest 包含 `formatVersion`、`backupId`、`kind`（AUTO/MANUAL）、`startedAt`、`completedAt`、`databaseVersion`、`sizeBytes`、`sha256`。源类型只用于展示与诊断，不改变 30 天清理规则。该文件是备份运行产物，不作为代码文件提交。

先在备份根目录内唯一 `.pending_<id>` 目录写入，最后写 manifest 并同卷重命名到正式目录；只有正式目录且 manifest 校验成功才算新格式的有效副本。重命名或落盘失败不更新成功时间。取消和失败清理由本任务创建的临时文件；重启后只处理可证明归属本应用的 pending 目录，不能递归清空未知目录。

旧格式只接受目录名严格匹配 `backup_yyyyMMdd_HHmmss`、合法时间及已知 DB/WAL/SHM 文件的直接子目录；将三件套复制到隔离临时目录，使 SQLite 在隔离副本执行必要的 WAL 恢复，再校验主库与结构。不能直接在外部旧文件上打开可写连接。旧目录时间用于估算创建完成时间，解析失败不猜测 `lastModified` 来执行自动删除。无法读取或校验失败的旧副本保持原位，保留 SAF 人工选择机会。

### 5. 最近成功时间与失败冷却

副本 manifest 为新格式完成时间的依据。SharedPreferences 只保存最近成功副本 ID/时间，以及本进程冷却与前台结果的辅助状态，不把失败尝试更新为成功。扫描发现缓存指向副本缺失或损坏时撤销缓存，以实际有效副本为准；成功发布后即使进程在写缓存前中断，也能从目录重建状态。

失败后同一进程 1 小时内不自动重试，计时使用单调时钟，前台切换和屏幕旋转不能绕过；新进程允许重新尝试，手动备份始终可发起。系统时间回拨或出现未来备份时，本轮跳过清理并补建当前时间副本。有效的最近成功 ID 优先处理该时钟异常：它仍在且时间不在未来时作为校准基点，避免旧未来目录永远压住新副本；缓存丢失时再做一次校准备份。时间异常不能引起每次打开都重复备份。

### 6. 清理规则

- 正常时间下，以检查开始时捕获的同一个 now 判断 `now - completedAt > 30 天`；恰好等于保留。
- 保护本轮最近有效副本及正在操作的目标；同时间副本用稳定 ID 决定保护对象。时钟异常不清理。创建失败不清理历史有效副本。
- 手动副本和验证通过的旧副本同样适用。扫描异常、权限不足、时间不可信、校验失败的副本不纳入删除候选。
- 每个目标删除前检查 canonical 路径在固定根目录之内且为直接子目录，不跟随链接；枚举允许文件，再逐项删除允许文件并删除空目录。目录含未知文件则整项跳过，不用无条件 `deleteRecursively()`。
- 删除前再次确认目标身份、保护集和文件归属；任意失败单独记录，继续其他候选。结果记录删除成功数、失败数、跳过数和原因。
- 备份超期不会精确在第 30 天后台删除，而是在下一次打开应用时维护。

### 7. Toast 与诊断

协调器输出结构化结果，由统一前台提示层在主线程消费，消息文案存于 strings，不在 ViewModel 拼 UI 文案。只保留每次操作的一条待消费结果，Activity 重建不重复显示，后台完成等到下次前台展示。

| 结果 | 提示 |
| --- | --- |
| 自动备份成功 | 数据库已自动备份：Download/bDouyin/backup/… |
| 自动备份成功、部分清理失败 | 数据库已自动备份，部分过期备份未能删除 |
| 自动备份失败 | 数据库自动备份失败：空间不足 / 无存储权限 / 校验失败 |
| 仅清理成功 | 不额外 Toast，避免频繁打扰 |
| 仅清理失败 | 过期备份清理未全部完成 |
| 没有到期操作 | 不提示 |

日志保留触发来源、最近有效时间、耗时、大小和清理计数，不输出标签内容或密钥。

## Risks / Trade-offs

- [事务内逻辑复制让业务写入等待] → IO 线程、逐行复制、仅复制本地数据库，实测并记录大数据量事务耗时；不能用主线程等待或复制活动 WAL 规避。
- [历史副本可能损坏或重装后无访问权限] → 隔离验证，无法确认时保留；继续提供 SAF 恢复入口。
- [公共目录被用户修改] → 发布后核验，扫描与删除前复核；未知文件和链接不删除。
- [设备进程被杀] → 完成标记与原子发布，下次前台重试，不承诺关闭应用后仍能完成。
- [30 天清理也涉及手动副本] → 明确写入设置页备份说明；原来手动确认与恢复流程不变，最近有效副本始终受保护。

## Migration Plan

1. 先实现快照与发布并通过隔离恢复测试，再接入前台触发；不修改 Room schema，不覆盖当前偏好学习改动。
2. 保留旧格式读取，验证通过后才参与周期和清理；无需批量重写旧目录。
3. 测试通过后更新 CLAUDE.md 及备份操作说明，再交付 Debug APK 和实际验证结果。
4. 回滚时可停用前台协调器；新副本仍保留标准 `.db`，可通过原 SAF 入口恢复。已清理的过期副本无法自动找回。
