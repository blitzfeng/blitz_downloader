## Context

当前短视频批量 AI 标签分析由前台服务 `AiBatchAnalysisService` 驱动，逐条调用 `AiTagSuggestionRepository` 与 `GeminiProvider` 执行大模型推理。
分析的进度与结果通过事件总线 `AiBatchAnalysisEvents` 通知到界面的 `BatchTagReviewViewModel`。
目前接口请求体与响应体的日志仅在 `GeminiProvider.LoggingInterceptor` 中通过 `android.util.Log.d` 打印到系统 Logcat，用户无法在 App 内查看接口实际交互的数据细节，且原始数据充斥着图片 Base64 编码等机器数据，不具备可读性。

## Goals / Non-Goals

**Goals:**
- 单个视频打标签弹窗提供日志入口，实时查看当前视频 AI 建议的请求、返回和失败原因，并支持复制。
- 在 `BatchTagReviewActivity` 的顶部操作栏新增日志入口按钮，点击唤起日志查看面板（BottomSheet）。
- 建立内存级日志管理组件 `AiAnalysisLogStore`，随分析过程记录每条视频的请求与响应数据（请求 prompt、文案、选帧信息、词表、接口原始响应 JSON、解析结果、token 消耗及耗时）。
- 对图片 Base64 实施脱敏过滤，用易读的概要代替。
- 对日志数据提供针对普通用户的友好格式化渲染：结构清晰的卡片布局、长文本与长数组以空格/换行规整分隔、支持折叠展开与一键复制。

**Non-Goals:**
- 不做持久化数据库存储：日志仅保留在当前 App 会话内存中，避免频繁写库占用手机空间。
- 不影响大模型主链路调用：日志收集采用旁路轻量记录，不增加网络耗时与主线程卡顿。
- 不改变既有的 AI 建议模型结构与交互逻辑。

## Decisions

### 1. 统一内存日志存储 `AiAnalysisLogStore` 与事件总线协同
- **决策**：创建单例或对象级 `AiAnalysisLogStore`（具备固定容量环形队列，如最多保留最近 100 条），在单个视频与批量分析共用的 `AiTagSuggestionRepository` 调用链路中，于请求开始时创建日志，并在完成或失败时更新同一条日志，并通过 StateFlow 供 ViewModel 订阅。
- **理由**：批量分析是前台服务驱动的，用户可能切走 Activity；将日志保存在独立内存 Store 中，可以保证 Activity 销毁重建后依然能完整查看本次批次的所有日志。
- **替代方案**：
  - *存入 Room 数据库*：过重，分析日志属于调试/辅助性质，且包含较长 prompt，大量写入数据库会迅速膨胀存储。
  - *仅在 ViewModel 里维护*：若服务在后台运行而 Activity 被系统杀死，日志会丢失。

### 2. 日志数据结构分层：概览层 + 原始报文层
- **决策**：日志条目 `AiAnalysisLogEntry` 同时保留“业务友好概览”与“格式化原始数据”：
  - **业务概览**：视频文案、抽帧人脸情况、候选标签与置信度、视觉观察、消耗统计。
  - **原始数据**：格式化带缩进的请求 JSON（已脱敏图片 base64）和返回 JSON。
- **理由**：普通用户重点关注“发了什么提示词和文案”以及“AI 给出的判断依据和标签”，开发者或高级用户关注原始 JSON；分层设计兼顾两类人群。

### 3. 长数据排版与空格分隔机制
- **决策**：
  - 针对标签列表：以徽章加空格间隔（如 `[ 颜值 (92%) ]   [ 穿搭 (88%) ]   [ 妆容 (75%) ]`），不得拥挤成一坨。
  - 针对长文案/长特征描述：按语义句读分行，并在冒号后留空格缩进。
  - 针对原始 JSON：使用 Gson `setPrettyPrinting()` 格式化缩进，长行字段在渲染时采用等宽字体与适度内边距展示。
- **理由**：满足用户“格式明晰，较长的数据采用空格分开，普通人能接受”的具体排版要求。

### 4. UI 呈现：ModalBottomSheet 折叠卡片列表
- **决策**：使用 Compose `ModalBottomSheet`，顶部提供“日志总数”、“清空”、“一键复制全部”，主体为可展开的 LazyColumn。每个视频条目显示标题、状态徽章、耗时，展开后分为「请求数据」和「返回数据」两个区域。
- **理由**：BottomSheet 不打断正在进行的批量分析界面，滑动与关闭自然，在手机端单手操作体验好。

### 5. 失败原因从接口响应传递到日志
- **现状**：`GeminiGenerateContentResponse` 未接收 `promptFeedback`，`extractText` 在缺少候选文本时仅报告“Gemini 返回结果为空”；日志虽有 `errorMessage` 展示，但服务端具体拦截原因在解析时已丢失。
- **决策**：接口返回 `ResponseBody`，由 `GeminiResponseParser` 读取原始响应 JSON，避免类型化反序列化丢弃诊断字段；在 Provider 解析响应时提取失败信息，并通过携带诊断数据的异常或等价结构传递给 Repository，由 Repository 更新同一条日志的失败状态、原因、响应详情、耗时和已有 token 统计。不得依赖 Logcat 文本反向解析。
- **原因提取顺序**：
  1. 存在有效 `promptFeedback.blockReason` 时，以请求被拦截处理，保留原因码及服务端提供的说明。
  2. 无请求拦截原因而候选结果出现导致无法形成有效建议的 `finishReason` 时，记录候选结束原因及说明，不得将不完整结果视为成功。
  3. 非成功 HTTP 响应保留 HTTP 状态码与可获得的接口错误信息；网络、解析异常记录具体异常信息。
  4. 以上信息均不可获得时，才使用“返回结果为空”或“未知错误”等兜底提示；未知原因码按原文展示，不因尚未识别而丢弃。
- **示例**：收到仅含 `promptFeedback.blockReason = "PROHIBITED_CONTENT"`、`usageMetadata`、`modelVersion` 和 `responseId` 的响应时，日志状态为失败，显示“请求被内容策略拦截（PROHIBITED_CONTENT）”。不得仅显示“Gemini 返回结果为空”，也不得据此猜测具体违规内容。
- **诊断保留**：失败详情保留接口响应 JSON（沿用现有脱敏规则），以及响应中存在的 token 消耗、`modelVersion`、`responseId`。无响应体的网络错误不伪造这些字段；HTTP 成功但内容拦截的响应同样进入失败日志。
- **展示一致性**：折叠卡片显示可读失败摘要，展开详情显示完整原因和响应数据；单条复制与全部复制包含同样的原因码、说明及已有诊断信息。成功日志继续沿用原有展示行为。

### 6. 单个视频打标签弹窗的日志入口与过滤范围
- **入口**：在 `TagEditDialogFragment` 的“AI 建议”操作区域增加明确的“日志”按钮，跟随 AI 建议功能开关显示；功能启用时，分析前、分析中、成功后和失败后都能打开。查看日志不触发新的分析请求。
- **范围**：以弹窗参数中的 `awemeId` 作为唯一过滤依据，由 `TagEditDialogViewModel` 订阅共享 Store 并暴露当前视频日志；不按文案、列表位置或“最近一条”判断归属。展示内存中仍保留的该视频记录，包含单次建议和批量分析产生的同视频记录。无记录时提示“当前视频暂无 AI 分析日志”。
- **多次分析**：每次实际请求保留独立日志 ID，重试追加新条目；进行中条目收到返回后原位更新为成功或失败，用户打开面板时无需关闭重开即可看到变化。沿用会话内存存储及容量限制，不承诺跨进程保留。
- **展示复用**：抽取 `AiAnalysisLogSheet` 中跨页面共用的日志内容到 `ui/`，供批量页与单视频弹窗使用；单视频日志容器沿用 `ComposeDialogFragment`，避免在既有弹窗内嵌套 Compose `Dialog`/`ModalBottomSheet` 产生额外窗口与遮罩。纯界面显隐状态由 Fragment/Compose 管理，ViewModel 负责日志数据流。
- **内容一致**：当前视频日志同样展示脱敏请求、接口返回、解析结果、耗时、已有 token 统计及具体失败原因，包括 `PROHIBITED_CONTENT` 等原始原因码。尚未发送请求的本地失败应明确说明，不能伪造请求或返回报文。
- **操作边界**：单条复制与“复制全部”仅作用于当前视频可见日志；若复用清空按钮，则仅删除当前视频日志，不能清空其他视频记录。打开或关闭日志不关闭打标签弹窗，不改变已勾选标签、不提交标签，也不重新发起或取消 AI 建议请求；返回键先关闭日志，再回到原打标签弹窗。

### 7. 历史参考案例管理与持久化排除
- 新增 `AiReferenceManageActivity`，使用 Compose + Material 3；设置页打开全部案例，日志条目通过当前视频 ID 解析作者后默认查看同作者案例，可切换全部。支持作者名/文案搜索、可用/已移除状态、按视频多选、参考图预览、移除与恢复。
- 使用独立表 `ai_reference_exclusion(awemeId, excludedAtMillis)` 保存视频级排除规则，数据库升级 v30。移除仅改变参考资格，不删除视频、实际标签、反馈记录或证据图；重启及对同一视频重新产生反馈后仍排除，用户恢复后重新具备采样资格。
- 历史反馈按视频聚合展示，包含完整文案、作者、采纳/拒绝/补充标签、参考图和状态。无反馈、搜索无结果及图片缺失均给出明确状态，不因图片读取失败阻止移除。
- 在 DAO 的参考查询中于排序/LIMIT 之前排除记录，覆盖同作者/全局多模态参考及文本样例。频率与审核准确率统计仍基于真实反馈，不因参考资格变化而改写。
- 变更排除规则的事务同时使旧偏好摘要失效，后续摘要只使用未排除的案例；异步生成摘要保存前核对排除规则快照，避免并发旧结果重新写入。管理操作本身不发起网络请求。
- 排除对保存完成后新组装的请求生效，不撤回已经发出的请求。日志是历史快照，移除案例不修改已有日志；采样可能改选其他未排除案例，用户可继续管理。

## Risks / Trade-offs

- **[内存占用]** 多条大文本 JSON 存放在内存中可能占用若干 MB 内存。
  → **缓解**：脱敏剔除图片 Base64（避免单张图片占用数百 KB），并设置最大容量限制（如 100 条环形缓冲区），新日志挤出最旧日志。
- **[JSON 格式化耗时]** 格式化长 JSON 可能在主线程产生轻微抖动。
  → **缓解**：在后台线程异步完成 Pretty Print 处理，UI 层只负责渲染纯字符串。
