## Context

当前短视频批量 AI 标签分析由前台服务 `AiBatchAnalysisService` 驱动，逐条调用 `AiTagSuggestionRepository` 与 `GeminiProvider` 执行大模型推理。
分析的进度与结果通过事件总线 `AiBatchAnalysisEvents` 通知到界面的 `BatchTagReviewViewModel`。
目前接口请求体与响应体的日志仅在 `GeminiProvider.LoggingInterceptor` 中通过 `android.util.Log.d` 打印到系统 Logcat，用户无法在 App 内查看接口实际交互的数据细节，且原始数据充斥着图片 Base64 编码等机器数据，不具备可读性。

## Goals / Non-Goals

**Goals:**
- 在 `BatchTagReviewActivity` 的顶部操作栏新增日志入口按钮，点击唤起日志查看面板（BottomSheet）。
- 建立内存级日志管理组件 `AiAnalysisLogStore`，随分析过程记录每条视频的请求与响应数据（请求 prompt、文案、选帧信息、词表、接口原始响应 JSON、解析结果、token 消耗及耗时）。
- 对图片 Base64 实施脱敏过滤，用易读的概要代替。
- 对日志数据提供针对普通用户的友好格式化渲染：结构清晰的卡片布局、长文本与长数组以空格/换行规整分隔、支持折叠展开与一键复制。

**Non-Goals:**
- 不做持久化数据库存储：日志仅保留在当前 App 会话内存中，避免频繁写库占用手机空间。
- 不影响大模型主链路调用：日志收集采用旁路轻量记录，不增加网络耗时与主线程卡顿。
- 不改变既有的 AI 建议模型结构与交互逻辑。

## Decisions

### 1. 统一内存日志存储 `AiAnalysisLogStore` 与事件总线协同
- **决策**：创建单例或对象级 `AiAnalysisLogStore`（具备固定容量环形队列，如最多保留最近 100 条），在 `AiBatchAnalysisService` 执行单条视频分析完成后（或失败时）写入日志条目，并通过 StateFlow 供 ViewModel 订阅。
- **理由**：批量分析是前台服务驱动的，用户可能切走 Activity；将日志保存在独立内存 Store 中，可以保证 Activity 销毁重建后依然能完整查看本次批次的所有日志。
- **替代方案**：
  - *存入 Room 数据库*：过重，分析日志属于调试/辅助性质，且包含较长 prompt，大量写入数据库会迅速膨胀存储。
  - *仅在 ViewModel 里维护*：若服务在后台运行而 Activity 被系统杀死，日志会丢失。

### 2. 日志数据结构分层：概览层 + 原始报文层
- **决策**：日志条目 `AiAnalysisLogEntry` 同时保留“业务友好概览”与“格式化原始数据”：
  - **业务概览**：视频文案、抽帧人脸情况、候选标签与置信度、视觉观察、消耗统计。
  - **原始数据**：格式化带缩进的请求 JSON（已脱敏图片 base64）和返回 JSON。
- **理由**：普通用户重点关注“发了什么提示词和文案”以及“AI 给出的判断依据和标签”，开发者或高级用户关注原始 JSON；分层设计兼顾两类人群。

### 3. 长数据排版与空格分隔机制
- **决策**：
  - 针对标签列表：以徽章加空格间隔（如 `[ 颜值 (92%) ]   [ 穿搭 (88%) ]   [ 妆容 (75%) ]`），不得拥挤成一坨。
  - 针对长文案/长特征描述：按语义句读分行，并在冒号后留空格缩进。
  - 针对原始 JSON：使用 Gson `setPrettyPrinting()` 格式化缩进，长行字段在渲染时采用等宽字体与适度内边距展示。
- **理由**：满足用户“格式明晰，较长的数据采用空格分开，普通人能接受”的具体排版要求。

### 4. UI 呈现：ModalBottomSheet 折叠卡片列表
- **决策**：使用 Compose `ModalBottomSheet`，顶部提供“日志总数”、“清空”、“一键复制全部”，主体为可展开的 LazyColumn。每个视频条目显示标题、状态徽章、耗时，展开后分为「请求数据」和「返回数据」两个区域。
- **理由**：BottomSheet 不打断正在进行的批量分析界面，滑动与关闭自然，在手机端单手操作体验好。

## Risks / Trade-offs

- **[内存占用]** 多条大文本 JSON 存放在内存中可能占用若干 MB 内存。
  → **缓解**：脱敏剔除图片 Base64（避免单张图片占用数百 KB），并设置最大容量限制（如 100 条环形缓冲区），新日志挤出最旧日志。
- **[JSON 格式化耗时]** 格式化长 JSON 可能在主线程产生轻微抖动。
  → **缓解**：在后台线程异步完成 Pretty Print 处理，UI 层只负责渲染纯字符串。
