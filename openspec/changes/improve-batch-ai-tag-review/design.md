# Design

## Context

动机见 proposal.md。当前 `mergeBatchVideos` 保留最新批次全部记录，`filterVideosForAnalysis` 仅剔除手动排除项；`reloadPendingGroups` 又复用此过滤结果构建建议组。直接向此方法加入编辑次数限制，会使当前会话内刚确认的视频从其他组及汇总消失。

`AiBatchAnalysisService` 只将成功建议保存到 `ai_tag_suggestion_pending`，失败只有 `ItemDone(succeeded=false)` 事件；事件流 `replay=0`，页面未订阅时无法恢复失败列表。确认完成后暂存建议会删除，内存中的 `sessionPendingRows` 无法支持页面重建后的完整结果。当前完成逻辑只检查分组或修改次数，不能区分未开始、全失败和无建议标签。

结果卡片的三个按钮实际为“跳过、反选、确认”。现有 Material 3 按钮已有默认按压效果，但异步执行状态、成功后卡片移位和失败反馈尚未形成完整交互。

## Goals / Non-Goals

**Goals:**
- 将候选资格、本次成员、AI 结果和人工审核状态分离，使过滤、编辑和结果清理各自有清晰范围。
- 后台服务先持久化结果再通知 UI，页面通过数据库恢复，无需依赖事件重放。
- 延续现有分组顺序、标签计数、用户编辑与 AI 反馈语义。

**Non-Goals:**
- 不修改 AI 提示词、模型、抽帧、下载批次产生门槛或自动补全标签规则。
- 不新增自动重试、历史会话浏览器或进程被杀后的网络任务断点续跑。
- 不将“打开编辑弹窗”或“保存未变化标签”计为一次标签修改。

## Decisions

### 1. 资格过滤与会话展示分开

在 `BatchReviewLogic` 提取统一资格判断：`mediaType == video && tagEditCount == 0`，先合并最近两个批次并去重，再计算候选列表与正确的批次数量。图集即使包含 mp4 实况资源也按记录的媒体类型排除。自动排除不可通过恢复手动排除项绕过。

`startBatchAnalysis` 重新读取数据库并计算最终提交名单。显示层的 `TagEditFilter` 只控制审核视图，不参与提交范围或完成计算。服务启动时建立本次成员快照，后续建议组、失败区和汇总从本次成员取数，当前标签则读取最新数据库值。分析开始后的编辑次数变化不再过滤本次成员。

未采用“每次刷新都重新套资格过滤”的方案，因为它会让跨组视频提前消失；也不从建议组反推本次成员，因为失败或空建议没有分组。

### 2. 持久化最近一次分析会话

增加 Room 会话与成员结果存储，命名在实现时遵循现有实体风格。会话记录唯一 ID、来源批次标识、开始时间及运行/结束状态；成员以 `(sessionId, awemeId)` 唯一，保存提交顺序、等待/分析中/成功/失败状态、失败原因摘要、可空 `analysisId` 与成功建议快照。持久化分组处理状态及恢复审核所需数据，清理 pending 不清理当前会话快照。当前标签以标签关联表为准，不复制为另一份权威数据。

服务携带会话 ID 写入每项结果后再发事件；事件仅作刷新提示，结果由 DAO 查询或 Flow 获取。新的成功项仍复用既有完整分析持久化流程。区分成功但无建议和失败；不以“没有 pending”推断失败。防止旧会话的迟到事件污染新会话。页面仅在最近会话的 `sourceBatchIds` 首项与当前最新下载批次 ID 一致时恢复该会话，不提供历史选择入口。新增批次时清空当前结果展示、手动排除及显示筛选状态，重新计算候选；观察最近批次的 Room Flow，使已打开页面也能刷新。旧会话仍保留到新分析被接受，但不能把不匹配会话的 pending 当成首次升级数据迁移；新的有效任务被接受后可清理旧会话专用数据，不能误删 AI 学习资产。

恢复时，若持久化会话有未结束成员且已无对应活动服务，将这些成员标为中断失败并展示原因，不假装成功，也不自动发网络请求。服务启动失败要保留可重试入口并退出运行状态。历史版本没有保存的失败记录无法反向重建；升级后仅迁移现有可恢复的 pending 建议，不伪造历史完整清单。

仅用 ViewModel 内存或将事件改为 replay 都无法在页面重建、结果暂存清理后可靠恢复，因此采用持久化会话。

### 3. 单个列表组合三类结果与全量汇总

`GroupsListSection` 改为始终能够承载结果的 `LazyColumn`，不再用 `groups.isEmpty()` 提前返回统一空状态。存在未处理项时隐藏“本次分析全部视频”，顺序为：未处理建议组 → 失败区域。全部处理完成后，顺序切换为：本次分析全部视频 → 失败区域。空类型不占位；“全部”展示后仍保留失败区域。已处理组的状态、渲染和撤销实现保留，但不加入列表。原有子标签/父标签及组内排序保持不变，失败区与汇总采用稳定且带区域前缀的 key。

失败区复用封面播放和单视频编辑能力，展示简明原因，详细错误仍在现有日志入口。人工保存后保留 AI 失败标识，并更新人工处理状态和标签。汇总按提交顺序去重，不受审核列表的编辑次数筛选影响。

完成条件使用未过滤的会话状态：本次非空、所有成员分析已结束、所有成功建议组处理完成。失败和空建议成功项无需额外审核组。汇总文案明确“分析成功/失败”和“待人工打标”，不将 AI 失败表述为已打标。保留撤销逻辑供后续复用，目前不展示已处理组及其长按入口。保存单视频标签时保持“全部”区域及稳定 key，不因 busy 状态移除列表项；仅禁用正在提交的操作，保留滚动位置。

### 4. 交互反馈与原子操作

保留 Material 3 默认按压效果，校验紧凑按钮的触控区域。反选即时显示勾选和选中数量；确认/跳过以组为粒度维护业务执行状态，执行期间禁用同组冲突操作。ViewModel 在调用入口防重，不能仅依赖 UI 禁用。

涉及标签、计数、反馈及审核状态的数据库写入应在一致的事务边界完成；仅提交成功才更新已处理状态。使用结构化一次性事件，经 `SharedFlow(replay=0)` 由页面展示 Snackbar 或 Toast，确保卡片移位后用户仍能看到成功或失败提示。当前先滚动再等写入完成的行为调整为成功后更新位置；失败保留原状态并允许重试。

### 5. 人工编辑复用现有计数与反馈规则

失败区和汇总统一走 `saveSingleVideoTags`，复用 `setTagsAsUserEdit`，仅实际标签集合改变时增加修改次数。取消、保存失败及保存相同集合都不增加次数；从空标签保存空集合不构成“人工打过标签”。以后重新进入时，是否排除仍以持久化的 `tagEditCount > 0` 为准。

成功视频从会话快照取得对应 `analysisId`，确保 pending 被清理后仍能更新该分析的纠偏反馈；失败视频没有有效分析记录时仅保存人工标签，不生成虚假 AI 反馈。人工修改与分组审核的状态更新串行化，避免旧异步状态覆盖刚保存的标签，已有反馈按既有逻辑更新而不重复累积。

## Risks / Trade-offs

- [筛选误删本次结果] → 候选与会话集合分离，回归验证跨组确认后视频仍保留。
- [失败事件在离页期间丢失] → 数据库为结果权威，事件只负责唤醒刷新。
- [计数或反馈重复写入] → 同组操作防重、事务写入和反馈更新幂等性检查。
- [升级前失败结果没有来源] → 不伪造旧失败记录，完整会话保证从升级后的新分析开始。
- [新增存储带来迁移成本] → 增量建表，不改已有下载与标签数据；限制会话保留范围，不复制日志大字段。

## Migration Plan

1. 实现时读取实际 `AppDatabase` 版本，追加增量迁移与 schema 导出，验证升级保留原有下载、标签、AI 资产及 pending 数据。
2. 先接入会话持久化及服务结果写入，再接入 ViewModel 恢复与页面展示；新会话只能在资格核验完成后创建。
3. 运行有针对性的逻辑测试、迁移测试和 debug 构建，并在设备验证离页返回及全部失败等场景。
4. 功能回退时保留新增表和向前兼容的 schema，通过代码恢复原入口；不使用破坏性降级迁移或清库。
